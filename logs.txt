Paper 1: Multi-Objective / Pareto-Front QIEA

Working title: "A Hybrid Quantum-Inspired Evolutionary Algorithm with Adaptive Rotation-Gate Control for High-Dimensional Pareto-Front Approximation: Application to Urban Waste Collection Routing"

Gap you're filling: The Soft Computing (2025) continuous-space QIEA paper and the King (2025/2026) quantum-annealing MOO papers both stay in synthetic benchmark territory or 2–3 objective cases. Neither validates on a real many-objective (4+) routing problem. That's your opening — extend qubit-encoded MOO to a real-world 4–5 objective VRP (distance, time, cost, emissions, workload balance) using your FADSE framework as the implementation backbone.

Methodology:

Problem formulation — formalize Sibiu waste collection as a many-objective CVRP (Capacitated VRP) with 4+ conflicting objectives.
Algorithm design — qubit chromosome encoding for route assignment; adaptive rotation gate (angle schedule informed by convergence diversity, extending the H-epsilon gate literature); hybridize with a decomposition scheme (MOEA/D-style) or reference-vector guidance for scalability to many objectives.
Two-stage validation:
Synthetic: ZDT1–6, DTLZ1–7, WFG1–9 test suites (standard, reviewers will expect these)
Real-world: CVRPLIB instances, then your actual Sibiu GIS/routing data
Baselines: NSGA-II, SPEA2, MOEA/D, a reference-vector-guided EA, and — since it's very recent — a QAOA-based MOO baseline (Kotil et al. 2025) to show quantum-inspired vs. actual-quantum-approximate performance.
Metrics: hypervolume, IGD/IGD+, spacing, spread, convergence speed, wall-clock runtime.
Statistical validation: Wilcoxon signed-rank + Friedman test across 30 independent runs per instance (standard EA-paper rigor).

Tools:

pymoo (Python) — has NSGA-II/SPEA2/MOEA-D and the full ZDT/DTLZ/WFG suite built in, plus hypervolume/IGD indicators out of the box. Fastest way to get baselines running.
jMetalPy — alternative/complement, good for many-objective indicators.
DEAP — for building your custom qubit-encoded QIEA from scratch (more control than pymoo for novel operators).
PlatEMO (MATLAB) — if you want a second, widely-cited platform for cross-validation of results (common in top-tier EA journals).
OSMnx + NetworkX — pull real Sibiu street network graph from OpenStreetMap and generate realistic routing distances/times for the real-world validation stage.
OR-Tools — sanity-check exact/near-optimal solutions on small instances to validate your Pareto front quality.

3. What each objective actually measures (full detail in problem.py's docstring)
   f1 distance (km)      sum of edge distances over all routes, depot round-trips included
   f2 time (h)            NOT proportional to distance: a per-edge log-normal "road factor"
                           models heterogeneous congestion/road type, independent of raw distance
   f3 cost                FIXED_COST_PER_VEHICLE * num_routes + variable fuel cost (scaled by
                           the same road factor) — genuinely depends on how many vehicles a
                           solution uses, not just total km
   f4 emissions (kg CO2)  distance + idling(time) + payload-dependent term; payload grows
                           monotonically along a route (a COLLECTION truck, not delivery), so
                           this is sequence-dependent and computed per route, not a static matrix
   f5 workload balance    std. dev. of per-route completion time across the vehicles used

   IMPORTANT: the first version of this pipeline made f2/f3/f4 pure scalar multiples of f1,
   which silently collapsed every Pareto front to a single point (caught by a pymoo sanity
   run). Fixed by giving time/cost/emissions independent random structure. Any future change
   to the instance generator should re-check for front collapse before trusting results.

4. Algorithm design rationale (qiea.py)
   Chromosome: one qubit angle theta in [0, pi/2] per decision variable (a real-amplitude
   simplification of the general qubit state), using the same rotation-gate math as the first
   paper's Eq. 3-4, generalized to a decomposition-guided update.
   Decode has two modes on the SAME representation:
     "permutation" (CVRP): tour = argsort(theta). Sorting real numbers can never produce a
        duplicate, so there is NO repair step. This directly fixes the scalability failure
        the first paper reported: "the potential problem of the QIEA on a high number of
        cities is the repair step ... the algorithm loses its diversity on high number of
        cities."
     "continuous" (ZDT/DTLZ/WFG): x_i = xl_i + sin(theta_i)^2 * (xu_i - xl_i).
   The same core loop (rotation, crossover, mutation, decomposition) validates on both the
   synthetic suites and the real-world CVRP, matching the plan's two-stage validation.
   Many-objective scalability: MOEA/D-style decomposition via Das-Dennis weight vectors
   (pymoo's get_reference_directions), Tchebycheff scalarization, T-nearest-neighbor
   mating/replacement — this is the "hybridize with a decomposition scheme" item from the plan.
   Adaptive rotation gate: step size decays over generations (explore -> exploit) but is
   boosted 3x whenever population angular diversity stalls for `diversity_window` generations
   — the "angle schedule informed by convergence diversity" item from the plan.

8. QIEA hyperparameter tuning pass (2026-08-12)
   New scripts: src/tune_qiea.py (first, naive sweep), src/tune_qiea_matched.py
   (population-fairness-corrected sweep). Both are OFAT (one-factor-at-a-time) sweeps
   on A-n32-k5, the cheapest instance, chosen because section 7 flagged neighborhood_size,
   mutation_prob, theta_max/theta_min, and H (via n_partitions) as first-guess defaults.

   a) First sweep (tune_qiea.py): swept all five knobs against qiea.py's defaults,
      5 seeds/config, n_gen=80. Best-looking single change was n_partitions=8 (H=495,
      up from the default H=126), +40% hypervolume.

   b) Fairness catch: n_partitions=8 for QIEA alone would have been an invalid
      comparison. run_baselines.build_algorithms() uses n_partitions=5 for MOEA/D's
      AND RVEA's reference directions too (same default as QIEA), so QIEA's H=126 is
      already exactly population-matched to MOEA/D and RVEA in run_experiment.py.
      Raising QIEA's n_partitions alone would just buy it more function evaluations
      per generation than the two baselines it currently loses to -- not a smarter
      search. n_partitions was therefore EXCLUDED from further tuning and left at the
      shared default (5). Only NSGA-II/SPEA2 use a separately-set pop_size (80-100),
      a smaller, pre-existing mismatch not addressed here.

   c) Second sweep (tune_qiea_matched.py): n_partitions held fixed at 5, resweeping
      neighborhood_size/mutation_prob/theta_max/theta_min (theta_min's range extended
      past the first sweep's 0.1 ceiling to check it wasn't a boundary artifact -- it
      wasn't; 0.1 is an interior optimum, values up to 0.25 were tested and were worse).
      Naively combining every individual "winner" (neighborhood_size=10 i.e. unchanged,
      theta_max=0.7, theta_min=0.1, mutation_prob=0.1) gave WORSE hypervolume than the
      unmodified baseline (8.56e11 vs 1.02e12) -- a textbook OFAT interaction trap.

   d) Explicit 2x2x2 factorial over theta_min/theta_max/mutation_prob (5 seeds each)
      showed the combined config loses specifically because theta_max=0.7 and
      mutation_prob=0.1 each interact badly with theta_min=0.1. Changing theta_min
      ALONE (keeping theta_max=0.35, mutation_prob=0.05, neighborhood_size=10 at their
      original defaults) was the single best-performing config in the factorial.

   e) Verified with 20 seeds, matched population, n_gen=80: theta_min=0.1 gives mean
      hypervolume 6.62e11 vs default's 5.77e11 (+15%), Wilcoxon p=0.044 (significant).
      qiea.py's theta_min default changed from 0.02 to 0.1 on this basis. This is a
      real, modest, population-fair improvement -- not a full fix for the "QIEA behind
      MOEA/D and RVEA" finding.

   f) Re-ran run_experiment.py on the same three instances as the 2026-08-11 pilot
      (A-n32-k5 n-runs=5, E-n101-k8 n-runs=3, route2_199 n-runs=3; all at n-gen=80,

9. Rotation-step scaling investigation (2026-08-13)
   Directly answers section 8f's open question. New script: src/tune_qiea_scaling.py.

   a) Mechanism: permutation decode is tour = argsort(theta) over theta in [0, pi/2].
      The average gap between adjacent sorted theta values is ~(pi/2)/n_var. A fixed
      absolute rotation step (theta_min/theta_max) is therefore an increasingly large
      multiple of that gap as n_var grows -- e.g. theta_min=0.1 is ~2x the gap at
      n_var=31 (A-n32-k5) but ~13x the gap at n_var=198 (route2_199), meaning the
      "exploit" phase late in the run keeps making disruptive, coarse moves relative
      to local tour structure on larger instances instead of fine-tuning.

   b) Screening sweep: theta_min/theta_max expressed as multiples of gap =
      (pi/2)/n_var, grid mmin in {0.5,1,2,4,8} x mmax in {2,4,7,14,28}, 3 seeds/config,
      n_gen=80, n_partitions=5 (matched to MOEA/D+RVEA), across A-n32-k5 (n_var=31),
      E-n101-k8 (n_var=100), route2_199 (n_var=198). Per-instance-best multipliers:
      A-n32-k5 mmin=2/mmax=7 (~matches the existing absolute default almost exactly),
      E-n101-k8 mmin=0.5/mmax=4, route2_199 mmin=0.5/mmax=7 -- mmin clearly needs to
      shrink relative to gap as n_var grows past ~31; mmax~7 is comparatively stable.

   c) Confirmed with 30 seeds + paired Wilcoxon (per-instance-optimal multipliers vs
      absolute default 0.1/0.35, matched shared reference point): route2_199 +18.1%
      hypervolume (p=0.0137, significant), E-n101-k8 +10.2% (p=0.119, trending, not
      significant), A-n32-k5 -4.1% (p=0.598, not significant -- i.e. no real change,
      as expected since the winning multiplier there is ~the existing default anyway).

   d) Single deployable formula (not per-instance-tuned values -- shipping an
      algorithm with per-instance hyperparameters would invalidate any fair
      comparison to the baselines, same fairness argument as section 8b):
        theta_min = min(0.1, 2*gap),  theta_max = min(0.35, 7*gap),  gap = (pi/2)/n_var.
      Both bounds are clamped to the OLD absolute defaults so the formula reduces
      EXACTLY to 0.1/0.35 at n_var<=31 (A-n32-k5, where they were originally tuned)
      and shrinks below that only for larger instances. Applies to permutation
      decode only -- continuous decode (ZDT/DTLZ/WFG) is unaffected, since there is
      no argsort step and no evidence this mechanism applies there.

   e) Bug caught before shipping: an earlier, unclamped version of theta_max
      (theta_max = 7*gap, no upper clamp) evaluates to ~0.3547 at A-n32-k5's
      n_var=31 -- a ~1.3% drift above the tuned 0.35. That tiny drift alone flipped
      QIEA from beating NSGA-II/SPEA2 (the documented section 8f state) to being the
      weakest of all five algorithms in a 5-seed run_experiment.py comparison,
      demonstrating the permutation-decode QIEA is quite sensitive to small
      rotation-step perturbations at small n_var. Fixed by clamping theta_max the
      same way theta_min already was; re-running confirmed A-n32-k5 now reproduces
      the committed pre-change results bit-for-bit.

   f) qiea.py's theta_max/theta_min constructor defaults changed from fixed
      absolute values (0.35, 0.1) to None, resolved at construction time via
      QIEA._default_theta_bounds(decode, n_var) using the formula in (d). Explicit
      values passed by callers (tune_qiea*.py, etc.) are unaffected.

   g) Re-ran run_experiment.py on the same three instances/budgets as section 8f
      (A-n32-k5 n-runs=5, E-n101-k8 n-runs=3, route2_199 n-runs=3, n-gen=80,
      pop-size=80), overwriting results/*_indicators.csv and results/*_fronts.npz:
        A-n32-k5    (32 nodes)  : identical to section 8f (QIEA beats NSGA-II/SPEA2,
                                   still behind MOEA/D and RVEA) -- exact
                                   reproduction, as designed.
        E-n101-k8   (101 nodes) : QIEA still weakest of the five -- UNCHANGED.
        route2_199  (199 nodes) : QIEA still weakest of the five -- UNCHANGED.
      The isolated, statistically-significant hypervolume gain from (c) did not
      change QIEA's RANK against MOEA/D/RVEA on either larger instance in this
      3-seed pilot. Conclusion: the scaling fix is real, mechanistically grounded,
      causes no regression, and measurably improves QIEA's own front quality on
      larger instances -- but it fixes the specific problem it targeted (why
      theta_min tuning didn't generalize), not QIEA's broader competitiveness gap
      against MOEA/D and RVEA on larger CVRP instances. That gap looks structural

   h) Open question for next session: with the rotation-step-scaling mechanism now
      ruled in (helps, doesn't fully explain the gap), the remaining section 7/8f

10. Mutation-rate scaling investigation (2026-08-13, same session as 9, follow-up)
    Directly answers section 9h's open lever. New scripts: src/tune_qiea_large.py
    (initial OFAT screen), src/tune_qiea_mutation_scaling.py (isolation sweep),
    src/tune_qiea_mutation_confirm.py (confirmatory run + interaction check).

    a) Initial OFAT screen (tune_qiea_large.py): neighborhood_size and mutation_prob
       swept together (n_partitions fixed at 5, theta bounds left on the section-9
       auto-scaled formula) on E-n101-k8 and route2_199, 5 seeds/config, n_gen=80.
       Combined best-per-param config (mutation_prob=0.01 + a much larger
       neighborhood_size: 50 on E-n101-k8, 20 on route2_199) looked enormous:
       +58.7% HV on E-n101-k8 (Wilcoxon p=0.0003, 15-seed confirm), +109.1% on
       route2_199 (p=0.0001, 15-seed confirm).

    b) Fairness/interaction check: A-n32-k5's existing tune_qiea_matched.py CSV
       already had mutation_prob=0.01 tested and it was WORSE than default there --
       opposite direction from the larger instances. Also, on E-n101-k8, the
       screen's mutation_prob-alone number (3.44e12) beat the "combined" nb+mp
       number from the confirm run (2.71e12) -- the same OFAT-interaction shape
       section 8c hit combining theta_min/theta_max/mutation_prob. Both signals said
       don't trust the combined config yet.

    c) Mechanistic hypothesis: quantum_mutation flips each gene independently with
       probability mutation_prob, so expected mutated genes per individual =
       mutation_prob * n_var -- the same "fixed absolute parameter, more disruptive
       as n_var grows" mechanism as section 9's rotation-step finding, just for
       mutation instead of rotation. Isolated sweep (mutation_prob only,
       neighborhood_size held at default 10) across all three instances, expressed
       as k = mutation_prob * n_var in {0.5,1,1.5,2,3,4,6,9.9}: A-n32-k5's own
       optimum sits at k~1.5-2 (matching its existing default almost exactly,
       0.05*31=1.55); E-n101-k8 best at k=1 (+70.4% HV, p=0.125, 5 seeds);
       route2_199 best at k=4 (+127.2% HV, p=0.0625, 5 seeds). Optimal k is not
       perfectly uniform across instances, but is clearly ~1-4 everywhere, versus
       the ~5-10 that a fixed absolute mutation_prob=0.05 produces at these n_var.

    d) Deployable formula, same clamping rationale as section 9d (not
       per-instance-tuned -- would break baseline fairness):
         mutation_prob = min(0.05, 1.55 / n_var)
       C=1.55 chosen so it reduces EXACTLY to the old default 0.05 at n_var=31
       (A-n32-k5) -- verified bit-for-bit identical mutation_prob there (no drift),
       learned from section 9e's finding that this representation is sensitive to
       even ~1% drift in a scale-family parameter at small n_var.

    e) 15-seed confirmatory run, matched population, isolating mutation_prob from
       neighborhood_size (held at default 10) to settle (b)'s interaction question:
         A-n32-k5:   formula reduces to mp=0.05 exactly -> bit-for-bit identical to
                     baseline, zero regression risk (as designed).
         E-n101-k8:  mutation-formula-only (mp=0.0155) vs default: +49.3% HV,
                     Wilcoxon p=0.0026 (significant). Adding back the screened
                     neighborhood_size=50 on top: -0.1% (p=0.978, no effect) --
                     confirms (b)'s suspicion; neighborhood_size's apparent gain in
                     the (a) screen was an OFAT interaction artifact of mutation_prob
                     still being wrong, not a real effect.
         route2_199: mutation-formula-only (mp=0.0078) vs default: +64.5% HV,

15. Plateau fix (2026-08-17, same session as 14): plateau-gated diversity
    reinjection ("restart") -- the largest, most general improvement found in
    this entire tuning investigation, shipped as the new QIEA default. Closes
    section 14g(i). New scripts: src/tune_qiea_restart.py (first grid screen),
    src/tune_qiea_restart_finegrid.py (boundary re-screen), src/tune_qiea_restart_confirm.py
    (20-seed confirm, all 7 instances). qiea.py gained restart_patience/
    restart_fraction constructor params and a QIEA._do_restart method.
================================================================================

    a) Mechanism: track generations-since-the-archive-last-grew. Once that count
       reaches restart_patience, reseed a restart_fraction of the H subproblems'
       theta to fresh uniform-random values in [0, pi/2] (immediately re-evaluated
       and folded into z_ideal), leaving every other subproblem untouched --
       elitist, unlike a full population restart. Verified the restart-disabled
       path (restart_patience=None) reproduces qiea.py's own smoke test
       bit-for-bit identical to pre-change behavior before any sweep was run.

    b) First grid screen (tune_qiea_restart.py): restart_patience in
       {20,50,100,200} x restart_fraction in {0.1,0.3,0.5}, plus a restart-
       disabled control, 5 seeds/config, n_gen=500 (the paper's actual budget,
       not the n-gen=80 pilots sections 8-13 tuned on), n_partitions=5, across
       A-n32-k5/E-n101-k8/route2_199 (the two plateaued instances from section 14
       plus a third for coverage). Result: EVERY SINGLE one of the 12 restart
       configs beat the control on EVERY instance (+4% to +59% hypervolume) --

    f) Conclusion: the plateau fix is real, general, large, and the correct
       explanation for section 14's finding -- it is not a tuning trick, it
       fixes an actual mechanism failure (the namesake "ARGC" escape not
       engaging). But fixing the plateau closes roughly half the ratio gap to
       the best baseline on average, not the gap itself -- QIEA still loses to
       all four classical baselines on 6 of 7 instances, and ties only the
       weakest baseline (NSGA-II) on exactly one (route1_334). The remaining gap
       is therefore NOT explained by the plateau/stagnation-escape failure alone
       -- something else about QIEA's per-generation search efficiency (most
       likely candidate, per section 14g(iii) carried forward: H/n_partitions,
       still untouched) accounts for the rest. This should be reported in the
       paper as exactly what it is: a genuine, large, well-validated ablation
       finding (the ARGC mechanism, once actually made to work, provides a
       real and necessary benefit) that improves but does not resolve QIEA's
       competitiveness gap against decomposition/reference-vector baselines.
